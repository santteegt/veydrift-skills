01

The one-paragraph version

An agent reads Veydrift's public game API, runs deterministic calculators against it, and proposes at most one action per tick — a typed Action, never signed bytes. A completely separate program builds the actual transaction for that action, checks it against its own independent allowlist regardless of what the first program already validated, and only submits it if a human types an exact confirmation flag. A three-tier policy field, edited by hand, is the only thing that ever lets more of that pipeline run for real. Nothing has ever submitted a transaction from this codebase to Veydrift.

02

Why two skills, not one

This isn't an accident of packaging — it's the load-bearing design decision, and almost every other choice in the repo follows from it.

allowlist re-derived independently — not trusted from the agent side

veydrift-agent is Python, reads an HTTP API, and never imports a signing library — grep -rn "viem\|ethers\|web3\|eth_account" skills/veydrift-agent/src/ returning nothing is an actual, checked invariant, not a description. veydrift-wallet is TypeScript, is the only thing that ever calls signAndSend, and independently re-derives its own allowlist from a live /runtime-config fetch and the pinned ABI — it does not trust anything the agent skill already checked. A fully compromised veydrift-agent can construct any Action it wants and hand it to walletctl build/simulate freely; it cannot make walletctl send submit anything without --confirm on that exact command line, and even then the destination, selector, and (at tier 3) mission type are checked again from scratch.

The practical benefit: the two languages can't accidentally share a dependency, a global, or a mutable object that lets a proposal bypass the allowlist. The practical cost: the two enforcement layers have to be kept in sync by hand across a language boundary — exactly the kind of thing that drifts silently. §8 covers how that drift actually happened once, and the test that now catches it.

The spec, reviewed

The full spec is docs/SPEC.md (620+ lines, v2.1). Read that for acceptance criteria and work-package breakdown; this section is what matters for the shape of the result.

Decisions taken, and why

DecisionChoiceWhy
API layerScripts, not MCPZero ops, native progressive-disclosure fit; an MCP server later would wrap the same module
Runtime splitPython reads, TS signsviem lives naturally in TS; the wallet engine is meant to be swappable independent of the planner
SchedulerOne idempotent tickHarness-agnostic — /loop, Hermes, bare launchd all call the same command
Config formatJSON, not YAMLA hand-rolled YAML parser was the actual weak point of an earlier draft, for a security policy
Wallet providerskeystore + envkey, both realTwo genuinely working implementations prove an interface is swappable; a stub proves nothing

What the spec explicitly does not attempt: combat, alliances, ACS, migration, referrals, NFT burns, the ERC-20 market bridge, and any raid-profitability model — protectedResources' actual semantics are unconfirmed, so nothing here builds loot logic on it.

The spec was wrong at least three times — and says so

Worth reading these specifically, because each describes a real defect that shipped and was later caught. Each is dated and marked as a correction, not silently rewritten as if it were always right.

Correction 1 — dead config

§4's original tier table never allocated startShipProduction to any tier, while the planner could propose it — a config knob (allow_ships) that could never actually work.

Correction 2 — an impossible example

§5.9's worked pretty-print example showed guards: 16/16 pass at tier 1, which is impossible — the tier gate must fail at tier 1 by definition. Left uncorrected, every tier-1 proposal would report decision=block and drown the promotion-evidence signal --readiness exists to surface.

Correction 3 — an unspecified trust boundary

§6.4 never said where walletctl should read the tier it enforces from — the implementation took it from the caller, which is exactly the actor the check exists to defend against.

If you're auditing this codebase, that inline history is worth reading — it's a record of what a reviewer should specifically re-check in code that looks similar.

│   ├── schemas/          # GENERATED — don't hand-edit
│   ├── references/       # 10 files, ~2,700 lines, on demand
│   └── tests/             257 tests

    ├── abi/               # pinned ABI + provenance — §6, §9
    ├── src/               # 10 modules, ~1,800 lines — §6

Both trees are self-contained on purpose: npx skills add copies only skills/<name>/ into wherever a harness keeps its skills, so nothing at the repository root travels with an install. Every citation inside a SKILL.md or references/*.md file to something outside its own skill tree is either a link to the sibling skill (explicitly framed as conditional), a link to the deployed contract's public GitHub source, or gone — internal-repo citations were deliberately stripped from both skills' shipped files once this was audited.

Runtime state lives outside this repo

$VEYDRIFT_HOME, default ~/.veydrift. Nothing under it is tracked by git, and no test should ever write there.

07

A tick, end to end

tier 1 always exits step 7 without sending — the tier gate BLOCKs before ALLOW is ever true

The decision ladder inside step 5, first match wins. Rungs 0-4 are vetoes; rungs 5-9 are a four-band candidate pipeline (candidates.py, added 2026-08-16, Phase 2 of the general-strategy-engine program, extended to a fourth band by Phase 4, same date — see §5):

plan.py + candidates.py — decision ladder
0. KILLSWITCH present               → HALT
1. /health not ok                   → NO-OP, reason recorded
2. pending tx unreconciled          → NO-OP, reconcile first
3. mission Resolving > 60s          → resolveFleetMission (permissionless, free)
4. incoming hostile fleet           → ESCALATE, no proposal at all
5-9. generate → filter → score → select, four bands in order:
     1. deadline-driven      -- storage overflow: spend it, or build the matching storage
                                 (Phase 3: proactive storage also visible as a Band-2
                                 alternative, never a Band-1 winner)
     2. economically scored  -- building upgrade, ascending payback hours
                                 (energy-first is a hard filter here, not a score;
                                 Phase 3: an explicit building_priority takes precedence)
     3. policy-declared      -- research (Phase 3: research_priority first, else
                                 lowest-level-first labelled "default:"), then
                                 ships/defense (Phase 3: ship_targets/defense_targets
                                 stock-keeping, plus scored Crawler), gated on
                                 economy-on-track
     4. unlock-chain (8b)    -- Phase 4: the shallowest buildable prerequisite toward
                                 a locked ship_targets/defense_targets/research_priority
                                 entry, score=None, reached only when bands 1-3 found
                                 nothing at all
     else                    → NO-OP, explicit reason

The winning Action also carries alternatives — the runner-up candidates from the same pass, ranked, each with a why_not (a payback-hours comparison, or a lock reason from techtree.describe()). Purely informational: never an ROI verdict, never read by guard.py or any Decision logic.

Phase 3 (2026-08-16) — every planet-local entity reachable

Before this change the planner could only ever propose 13 of the 51 entities ids.py knows. policy.strategy grows four target-declaration fields (ship_targets, defense_targets, research_priority, building_priority, all defaulting to []) that drive the rest without inventing a doctrine: the engine computes what's legal (techtree.unmet()), affordable (guard.py, unchanged) and economically comparable (score_payback); the policy declares intent for everything else. [] on all four is this phase's own acceptance criterion — byte-identical output to Phase 2, pinned directly in tests/test_candidates.py/tests/test_plan.py and by every pre-Phase-3 test passing unmodified.

Phase 4 (2026-08-16) — a locked declared target proposes its own build-up

Phase 3 made every entity reachable once its prerequisites are already met; a ship_targets/defense_targets/research_priority entry the account cannot build yet was still a dead end — legal to want, correctly never proposed, and nothing ever proposed the prerequisite that would unlock it. New techtree.next_step_toward(family, entity_id, *, building_levels, technology_levels) -> UnlockStep | None walks unmet()'s output backwards, breadth-first, to find the shallowest requirement in the chain that is itself buildable right now — its own unmet() is empty and its own current level is known (an UnmetRequirement(have=None) can never become a confidently-chosen step). Cycle-safe and depth-bounded defensively, though the real tables are asserted acyclic by test. candidates.generate_unlock_chain_candidates/select_unlock_chain_candidate turn the result into ladder rung 8b, score=None always — deliberately the last rung, checked only once every earlier one has produced nothing, so it can never outrank the storage-overflow deadline or displace a scored economic or policy-declared candidate. guard.py's prerequisites gate needed no code change (it keys off Action.kind, not the generator that produced it). Empty ship_targets/defense_targets/research_priority reproduces Phase 3's output exactly — this phase's own acceptance criterion.

--dry-run is the default at tier 1 and cannot be disabled there — doubly enforced: even if it were somehow bypassed, guard.py's own tier gate BLOCKs every onchain function below its minimum tier, so step 7's ALLOW condition is never true at tier 1 either. Two independent reasons landing on the same outcome is intentional redundancy, not accidental duplication.

08

The two independent enforcement layers

guard.py's _MIN_TIER_FOR_FUNCTION (Python) and allowlist.ts's ECONOMY_SIGNATURES / LAUNCH_FLEET_MISSION_SIGNATURES (TypeScript) encode the same tier policy in two languages, on purpose — the wallet engine re-checks independently of whatever the agent already validated, so a compromised agent can't talk its way past the allowlist by lying about the tier. They drifted once: startShipProduction was granted to the economy tier's table in the spec while allowlist.ts and the original guard.py map both still excluded it — Correction 1 in §3 — and nothing caught the mismatch for a while.

The fix wasn't just adding the missing entry — it was adding a test that parses allowlist.ts directly (regex over the const ECONOMY_SIGNATURES = [...] block) and diffs the resulting set against guard.py's own map, failing with the exact names on each side if they ever disagree again.

Not a "remember to update both" comment

A comment doesn't run in CI. If you're adding a new tier-gated function, test_tier_map_agrees_with_the_wallet_engines_allowlist is the one to run before you're done — not just the two suites separately.

09

Silent-corruption traps

Two things about the deployed contract produce a wrong transaction, not an error, if you get them wrong — expensive precisely because nothing crashes.

The 14-slot fleet tuple is not the 16-entry Ship enum

Every fleet entrypoint takes a fixed (uint32 × 14) tuple, but SolarSatellite (id 9) and Crawler (id 15) can't fly and have no slot — every flyable ship id from 10 upward is shifted down one tuple index. A Destroyer, Ship id 10, lands at tuple index 9, not 10. shipCountsToFleetTuple() is the only function permitted to build this tuple; the test pins a Destroyer at index 9 specifically, and the function throws on a non-flyable ship input even at count zero.

launchFleetMission is overloaded

A 7-arg and a 6-arg form both exist on the deployed ABI simultaneously. Selecting by bare function name is genuinely ambiguous to both viem and ethers — resolveFunctionAbi() requires the full canonical signature string everywhere in this codebase, never a name lookup.

Six functions that look like writes but aren't

protectedResources, raidableResources, maxRaidLoot, debrisField, collectResources, attackProtectionStatus are declared nonpayable — no view/pure modifier — because they lazily settle state before returning, not because they're meant to be sent as transactions. walletctl send refuses all six unconditionally, at every tier, even with --confirm; the correct path is simulate, or you pay real gas for what is semantically a read.

10

How this was built, and what that explains

This repo was built by a multi-agent pipeline: a planning pass wrote docs/SPEC.md, parallel Sonnet-model builder agents implemented independent work packages against that frozen spec, and Fable-model judge passes adversarially reviewed the result twice. That history is directly visible in the code.

Two real defects survived 316 passing tests

Both living exactly at the seam between the two languages — the place neither side's own test suite could see:

TSGas units compared against a wei ceiling
walletctl build emitted estimateGas's result — gas units — and tick.py compared it directly against gas_per_tx_wei — a wei ceiling. A typical Base transaction is ~10⁵ gas units against a 3×10¹⁵ wei ceiling: the gate could never fire, at any gas price.
Fixed: build now emits estimatedCostWei (gas units × live maxFeePerGas) as a decimal string, null rather than a substituted zero on a failed fee fetch, plus a dedicated unit-boundary regression test.
PYReverted transactions logged as successes
tick.py never read receipt.status. A reverted transaction was logged to actions.jsonl — the "executed only" audit trail — as a success, and AgentState.record_revert was called by no production code at all, so the revert_streak gate could never fire.
Fixed: receipt reports the real status; tick.py charges actualCostWei and calls record_revert on a revert; an unfetchable status is treated as unknown, never success.

The second judge pass found the residual gap after the first round of fixes: the allow_ships policy flag was enforced on one path that could emit a ship-production action but not another — a hot planet's energy-first branch could still propose a Solar Satellite regardless of the flag. Same defect class as the tier-map drift in §8: two things that needed to agree, and nothing forced them to.

The transferable lesson

A config flag or an enforcement rule that's checked in one place and emitted from two is exactly where the next bug is likely to live. If you add a second path that can produce the same kind of Action an existing gate already checks, verify the gate actually covers the new path.

11

What's tested, fixture-only, and genuinely unverified

Precision matters more here than a clean "it's tested" claim would suggest.

  • 257 Python + 104 TypeScript = 361 tests, all passing. They cover a system with two enforcement layers that must agree (§8); neither suite alone would catch a drift between them.
  • The read → plan → guard pipeline is exercised against the live API — vd calc verify re-runs three independent duration formulas against the real backend and confirms universe_speed == 1 still holds.
  • tick.py's tier-2+ send path has real, substantive test coverage — mocked at the walletctl subprocess boundary, asserting on execution counts, revert counts, the gas ledger, and log contents. It has never run against an actual chain. The first real run of the full build → simulate → send → await receipt → await indexed sequence will be someone's actual tier-2 promotion.
  • Cost scaling, queue behavior under load, and lazy settlement above level 0 are unobserved — not undertested, unobserved. The reference account has taken zero on-chain actions: every level is 0, every queue is idle.
  • walletctl's tier check defends against a misconfigured caller, not a hostile one. It falls back to a caller-supplied --tier when no policy file exists — a process that controls its own environment can point VEYDRIFT_HOME at an empty directory and assert any tier. Documented, not fixed — the fallback is legitimately needed for standalone use.

13

Extending this system

Adding a new guardrail gate

Belongs in guard.py, following the pattern every existing gate follows — return a GuardVerdict, resolve missing data toward BLOCK/ESCALATE rather than PASS, and add both a happy-path and a missing-data test.

Adding a new tier-gated action

Update guard.py's _MIN_TIER_FOR_FUNCTION and allowlist.ts's selector sets in the same change, then run the cross-layer sync test before anything else.

Adding a new wallet provider

Implement WalletProvider, wire it into provider selection, and — the standard the existing two set — make it a genuinely working implementation with its own address-derivation test, not a stub. Read docs/wallet-provider-research.md first; it rules out most hosted/MPC options against the address-binding constraint before you start.

Re-pinning the ABI after a contract upgrade

Recipe in AGENTS.md §6. Never build from main on the contracts repo — it has already drifted from the deployed implementation once, silently.

Before shipping any change

Both test suites, a live vd tick --dry-run, and — for anything touching the write path, tier model, or a guardrail — a fresh adversarial review pass. Two judge passes on this codebase have each found real defects the builder and the test suite both missed.
